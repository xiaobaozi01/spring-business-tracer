# 纯文档设计

## 架构变化

工具包不再运行一个独立的软件系统。删除自定义插件、状态引擎、配置解析器、图投影/分片引擎、23个自定义工具、20份Schema、依赖清单和脚本测试；没有把实现藏到其他目录或让Agent临时生成代码。

保留三个Agent、四个Skill、13个命令及一个入口笔记模板。全部是Markdown，YAML frontmatter只用于宿主发现和权限设置。

Agent定义“谁做、能使用哪些宿主工具”；Skill定义“怎么分析、什么证据足够”；命令定义“用户要做哪件事”。工作进度是可读的文档，不是需要模型操纵的机器协议。

## 参考与采用方式

| 参考 | 采用的原则 | 实现位置 |
|---|---|---|
| [Everything Claude Code / ECC](https://github.com/affaan-m/everything-claude-code) | 职责、复用知识、快捷入口分层 | Agent / Skill / command各自维护一类内容 |
| [BMAD Method](https://github.com/bmad-code-org/BMAD-METHOD) | 任务有明确范围，步骤按复杂度选择，交付物承接上下文 | 单入口直接追踪；全量先列入口；增量先评估变更；Markdown交接 |
| [Superpowers](https://github.com/obra/superpowers) | 在结论前取得证据，独立检查，任务边界明确 | 新reviewer会话复核；失败给具体证据缺口；不靠自报“已完成” |
| [Anthropic Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) | 简短入口与按需参考资料 | 共同规则只维护一份，领域细节按当前任务加载 |
| [Anthropic Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) | 从简单、可组合的工作流开始 | 原生Task + 原生文档工具，无自建运行框架 |

这里提炼工作方式，不要求安装这些项目或复制它们的全部角色。

## 为什么保留这三个角色

编排者需要写入文档并控制范围；分析者需要专注源码推理；复核者需要从独立上下文核验证据。这是三个实际不同的权限和上下文边界。

配置、覆盖、边界、增量不是五个不同身份，只是复核任务的不同范围。主Agent在交接中说明本次检查什么，无需新增报告kind协议或独立审计角色。

默认顺序处理入口。需要并行时只并行互不依赖的读取/分析，主Agent单点写入。不为同一run引入租约、心跳、fencing token和并发写事务。

## 能力怎样实现

| 用户能力 | 新实现 |
|---|---|
| 入口发现、逐跳链路、跨服务、数据库分析 | analyst按领域方法调用现有Code Graph并读源码，返回带证据的笔记 |
| 全量扫描 | 每服务入口清单 + 覆盖复核 + 逐入口交付 |
| 增量 | Git变更路径与笔记中的服务/共享模块/文件/配置依赖对照，无法证明时重查 |
| 暂停恢复 | plan保存具体入口、未完成分支和下一次查询；恢复先对比版本与范围 |
| 配置context | 对任务相关的本地声明做静态解释；复杂或外部来源保持未知，不重写Spring解析器 |
| 业务查询、解释、拓扑和表查询 | 读取Markdown索引和相关服务页，沿证据链接追溯 |
| 影响分析 | 从已确认Java符号查询真实callers，跨服务只经过已确认逻辑关系 |
| diff | 依据稳定入口键与关系身份比较文档版本；范围变化和业务删除分开 |
| 发布 | 先保存结果与复核，再更新索引，最后更新current链接；中断后核对文件继续 |

用户操作能力保留，执行保证发生变化：文档恢复不是事务恢复，独立复核不是机器认证，静态配置解释不是运行时配置求值。Skill如实表达这些边界，不声称拥有已删除代码提供的能力。

## 如何控制内容增长

Skill主体只保存共同规则和任务路由；Spring入口类型和跨服务/数据库细节各有一份参考。命令不复制流程，Agent不复制检查清单，输出只保留一个必要模板。

增加框架支持时先补领域参考和行为场景；不要重新引入脚本、Schema注册、工具适配层或插件。只有用户明确改变“无代码”要求时，才重新讨论程序实现。
