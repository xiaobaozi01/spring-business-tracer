# 工作流

## trace：一个入口

接受 HTTP method/path、完整 Java 方法签名或已记录的入口ID；歧义先消除。按 workspace 的 Doctor 确认后，建立一个 scope=单入口 的 run，写清楚本次范围。

1. 给 analyst 一个入口；按分析 Skill 返回调用链、边界、数据库访问及证据。
2. 将笔记保存到 run 草稿目录；更新 plan 中这个入口为待复核。
3. 新 reviewer 会话核对笔记。通过后保存带复核意见的结果；需修改则交回 analyst，只重查问题分支。默认最多修订两轮，仍无证据就标 PARTIAL，不循环猜测。
4. 根据结果更新该 run 的索引和当前发布链接。单入口完成只能说明该入口，不能声称全项目已扫描。

## scan：全量入口

先完成所选服务的入口发现。每个服务让 analyst 按入口类型返回清单，包括零命中类型、排除项和未知项。主 Agent 分服务保存 inventory，再让 reviewer 从源码独立检查覆盖。

清单确认后，逐个入口执行 trace 的分析/复核过程。不要先生成整套调用链再统一保存。所有入口都有结果、覆盖复核完成且无遗漏，才可称范围内扫描完成；任何未确认类型或分支仍保留 PARTIAL。

`--new` 新建 run；`--resume runId` 进入恢复。`--services ids`、`--contexts ids` 定义并记录本次范围；`--batch-size N` 仅控制每轮处理数量，不创建租约；`--max-agents N` 仅限制独立 Task 并发。用户未指定时顺序处理，不引入调度框架。

## update：增量

`--base current|runId` 必须找到已完成的文档基线。先读取基线 plan 中的范围、Git revision、dirty 标记、索引身份、context与工具包版本，再取得当前 Git 状态及变更路径；使用宿主 Git 工具或只读 git status/rev-parse/diff/log，不编写脚本。

重新发现整个所选范围的入口，比较稳定入口键。按每条旧笔记记录的服务/共享模块/文件/配置依赖分类：新增、需重查、可复用、已删除。变化触及其依赖就重查；基线或当前是无法对比的脏工作树、变更记录不全、依赖清单不全、索引语义/Skill版本改变时，相关范围全部重查。不能把“git status看起来相同”当内容未变的证明。

让 reviewer 复核变更集合及复用理由，再分析新增/受影响入口；复用项链接到原笔记并注明基线，不假装重新执行过查询。只有重发现与覆盖复核确认后才能记录删除；移出本次范围不是业务删除。

## pause / resume / status

pause：停止领取新入口，把当前已得到的证据和未完成分支写回草稿与 plan；记录下一个入口/符号/查询及原因，标 PAUSED。不要把笔记里“分析中”视为可自动回收的租约。

resume：读取指定 run 的 plan、inventory和草稿；未指定run时从当前工作记录选择唯一未完成任务，多候选时询问。重新检查范围、Git/索引/context和工作树状态；一致才跳过已复核项，变化不明则标过期并重查受影响范围。恢复点来自文件，不依赖聊天历史。

status：只读取 plan 和 inventory，逐项汇总已复核、待复核、待分析与缺口；数量来自表中实际行，不能凭记忆估计。仅查询状态不启动扫描。

## 发布与中断

文件结构见 [文档约定](artifacts.md)。先写结果和复核意见，再写 run 的汇总页，最后更新 current.md 的链接；未完成的草稿不加入正式索引。中断后逐个核对链接和文件内容，补齐缺失步骤；不宣称原子事务或机器验证过的哈希。

一个 run 只允许一个主会话写入。需要另一个会话接手时，先暂停旧会话；无法确认旧会话已停止就新建run，不并发覆盖同一份记录。
